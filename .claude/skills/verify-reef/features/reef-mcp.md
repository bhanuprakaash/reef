# reef mcp

A teammate's agent reaches the work item's memory through `reef mcp`, a stdio MCP server.
`reef token` (or `reef chat`, or `reef serve` for each teammate session, deleting it when that agent stops) makes a token for one role in one Space; `reef mcp` reads
it from `REEF_TOKEN` and serves 24 tools on that Space: the memory tools `remember`, `recall`
and `read_memory`, `get_brief`, the Space and wrap-up tools, the sub-item tools, `propose_work_item`, `submit_for_review`, and the browser
tools. Contract: `docs/memory.md`.

## Sub-work items

- `mcp-token` `reef token <work-item> --role R` makes Space `<role> (claude code)` and a 64-hex token, and prints a `claude mcp add reef --env REEF_TOKEN=... -- <reef> mcp --data <dir>` line. No `--role`, or an unknown work item, fails and makes nothing.
- `mcp-tools` `tools/list` names exactly the 24 tools.
- `mcp-read` `get_brief` returns only the brief; `read_memory` and `recall` return the memory items the token can read; `read_thread` and `search_sessions` return the work item's rows as JSON text; `read_thread` with `root` returns one thread.
- `mcp-write` `remember` writes an `accepted` item with the token's role as author and role, in scope `work_item` (the token's work item, the default), `project` or `teammate` (the role), with a `source` link to the token's Space; its `replaces` retires an item of the same scope. `propose_wrap` stores a pending proposal with its items; `post_to_space` stores a message with the token's role as author, and a reply when `parent` is given.
- `mcp-scope` an item or Space of another work item is `not found` and `recall` does not find it; `remember` refuses scope `team`, and `recall` with scope `team` and `propose_wrap` with a `team` item are refused on a solo Space; `search_sessions` finds only the token's work item's messages; on a quick-session Space every tool fails with `this space has no work item`, except `post_to_space`, `read_thread` of the token's own Space (also with `root`), `recall`, `read_memory` and `remember` (default scope `space`, or `project` or `teammate`).
- `mcp-sub-items` `create_sub_item` adds a `backlog` sub-item under the token's work item, type `task` unless given, and `GET /work-items?parent=ID` lists it; `list_sub_items` and `read_sub_item` read only that work item's sub-items; `set_sub_item_status` is refused for a teammate that is not the Space's lead, and the lead's call goes through the one status function, so a sub-item that is done does not move again.
- `mcp-propose-work-item` `propose_work_item` from any Space of a project, a direct conversation too, adds a top-level `backlog` item with `proposedBy` the token's role and `suggestedTeamId` the Team whose responsibility text best matches (the `solo` team when none does), and a `proposed` FYI in `GET /inbox`. With Teams `frontend` and `infra`, a failing deploy suggests `infra`. The item stays `backlog` with no `teamId` and no new Space or turn until the user queues it.
- `mcp-submit-for-review` the lead's `submit_for_review` with 2 of 3 acceptance lines ticked and one note sets the item to `review`, and `GET /work-items/1/proof` shows the lines, commands and screenshots as sent; a developer's token is refused; an open sub-item refuses it and names that sub-item, and nothing is stored.
- `mcp-plain-claude` plain Claude Code, given the server line `reef token` prints, calls the tools; what it writes has the token's role as author.
- `mcp-tool-errors` bad arguments come back as a result with `isError=true`, not a crash; an unknown tool is a JSON-RPC error.
- `mcp-no-token` no `REEF_TOKEN`, or an unknown one, exits 1 before serving.

## How to get to it (user POV)

- `reef token 1 --role developer`, then run the printed `claude mcp add` line; Claude Code then calls `mcp__reef__<tool>`.
- `reef chat` starts the agent with `reef mcp` already set up (see `chat.md`).

## Driving it with verify-reef

`$H mcp-call TOOL [JSON]` starts `reef mcp --data <run folder>` with the caller's
`REEF_TOKEN`, does the MCP handshake, lists the tools, calls one, closes stdin and waits
for the exit. It prints and logs to `reef-mcp.log`: `> TOOL JSON`, `tools: ...`,
`< isError=false|true <text>`, `reef mcp exit: N`, and any stderr. It exits 0 when a tool
result came back, 1 otherwise.

## Gotchas

- `mcp-call` is a scripted MCP client, not a model. Proof that a real agent calls the tools through its own MCP client is the Plain Claude Code step, and the in-chat tool calls in `chat.md`.
- `--strict-mcp-config --mcp-config FILE` gives that one `claude -p` the `reef` server and ignores the user's own MCP servers. `--allowedTools` lets the tool run without a prompt. It writes no config.
- Every Bash call is a new shell. Put `REEF_TOKEN=<token>` on each `mcp-call` line.
- Empty lists come back as `null` (`{"hits":null}`, `{"messages":null}`), not `[]`.
- Never run the printed `claude mcp add` line during a verify run: it writes the user's Claude Code config. Use the `--mcp-config` file above.
