# Window

A user opens the Reef window in a browser at the address `reef serve` prints. They start a
space on a feature, chat and watch the agent's tool calls and text arrive live. A new
space of the same feature starts from the brief. A free Space can be attached to a
feature, and a Space that hits a cap pauses and says why. A Space on a team names the running teammate, opens replies in a Thread pane. Contract: `docs/server.md`
(Web UI, Spaces live, Wrap-up and attach, Caps).

## Sub-features

- `window-live` a claude Space on a feature: a tool-using prompt shows tool rows while the turn runs; when it ends the reply is one stored `lead` message and the live view is gone.
- `window-brief` a new Space on a feature whose brief exists answers the goal from that brief.
- `window-attach` a free Space attached to a work item from the header button and dialog: the sidebar moves the Space under the work item; the free-Space turns' checkpoints, taken in the project folder, no longer show a Roll back button; the Attach button is gone.
- `window-cap` a Space whose token budget is used shows a banner with the reason and a disabled composer, keeps it after a reload, and the next message runs after Continue.
- `window-pages` a bad project path shows the server's error; a work item can be added from the sidebar.
- `window-stop` Stop mid-turn shows `Failed: interrupted` and the partial reply once; the next message resumes the session.
- `window-wrap` Wrap up shows the proposal panel, Reject leaves the brief unchanged; `/wrap` then Approve makes brief version 1 and closes the Space: Wrapped and Reopen replace Wrap up and the composer, the Space is under Wrapped (1) in the sidebar. Reopen brings the composer back; Close feature on the feature page lists it under Closed (1).
- `window-teams` the team picker makes a `duo` Space; the live turn names the lead, then the architect; a reply in the Thread pane is answered by the architect and the root shows `2 replies in thread`; in a `full` Space the lead hands off to the developer and the developer runs with no approval (the recipe is in `teams.md`).
- `window-retry` a failed turn shows a card with Retry; Retry runs the same wake as a new turn that ends `done`, and the row goes.
- `window-rollback` a Space with checkpointed turns lists them under Checkpoints, newest first, each with Roll back; Roll back asks to confirm, then the feature's worktree has the same HEAD, `git status`, `git log` and files as before the turn, `reef` posts `Rolled back to before turn N.`, and the next turn's prompt starts with that note.
- `window-inbox` the Needs you row and `/inbox` list what waits on the user, live from `/inbox/events`: a new waiting item of a Space that is not open shows with Open and Dismiss and fires one desktop notification; clicking an item, or its notification, opens its Space scrolled to and marking the item (the failed turn row, the pause banner or the newest message); an item of the Space open and visible fires no notification. `/inbox` groups its items under Needs you (paused, held, failed), Review and FYI; only FYI rows have Dismiss, and the three FYI kinds fire no notification.
- `window-diff` a feature's review page (`/features/{id}/review`, reached from the diff side panel's expand button or the feature page's header meta line) lists `GET /work-items/{id}/diff`: a turn that writes a file in the worktree, uncommitted, shows there as `A new.txt` with its added line.
- `window-memory` the project page (`/projects/{id}`, from the project switcher's Open project) lists the project's memory items (`GET /memory?scope=project:ID`), none for a new project; Add (kind and body) stores an accepted `project:ID` item with author `user`, it survives a reload, and Retire sets `retired_at` and drops it from the list. A feature page lists the feature's `work_item` items, one saved with `reef memory add` shows, and Retire there does the same. The page also has a Base branch field: a name that is not a branch name is refused, `dev` is stored in `project.base_branch` and survives a reload.
- `window-inspector` a Space's Inspector panel shows `GET /spaces/{id}/inspector`: totals (cost, tokens, turns) summed from the roles, one row per role that ran with its turn count, tokens and cost (`n/a` when the API has none) from the API, and every turn newest first; a developer turn expands to its prompt and a tool call with its name, input and result.
- `window-review` the review page lists files with A, M or D (a deleted file struck through, a file without hunks shows No text changes); clicking a line opens a comment box; drafts show under their line and are counted per file; Send to Developer posts them as one message, `path:line` per comment, to the developer's latest thread and clears the drafts.
- `window-workshop` the `/teams` page edits a role's persona and picks its creature (`face`) and saves both to the role row, its `mcpServers` unchanged; an invalid team (two leads, unrestricted `Bash` on a role without `write`) shows the same error as `reef team apply`; picking skills (a name not on disk shows as missing; a Codex role is offered only Codex skills) and allowed tools (checkboxes, a custom pattern field, hidden on a Codex role) and removing an MCP server saves to the role row; Settings lists the project's skills by provider; Duplicate makes a new team; the next developer wake's prompt carries the new persona.
- `window-capture` the `/capture` window picks a project and takes a kind and text; a successful capture shows "Captured", clears the text box and stores a task; a failing request (a deleted project) shows its error.
- `window-first-run` the project step shows Choose… only with the desktop bridge, and choosing a folder fills the repo path.
- `window-pr` the Space header's `PR #N` chip opens a PR panel in the Space's side panel from `GET /work-items/{id}/pr` (title, number, state, base and head, review, each check with a passed, failed or pending icon, an external Open on GitHub link); Merge is disabled until gh calls the PR mergeable, Cancel in its confirm dialog merges nothing, confirming runs `gh pr merge 12 --merge` once and the panel shows Merged.
- `window-theme` Settings shows Appearance (Dark, Light, Match macOS) and Notifications; picking Light restyles the open page at once and survives a reload; Match macOS follows `prefers-color-scheme` (emulated over CDP) both ways; text on the Space, inbox and feature page is at least 4.5:1 against its background in dark and light.
- `window-coordination` teammates' direct messages show in the Space as one compact item (`Lead and architect are coordinating · N messages`) and never as bubbles; the item updates in place and says working, paused, failed, stopped or completed; it opens a Coordination panel that shows the running recipient's text growing live, then the full ordered exchange (sender, recipient, time, delivery status), a link to the public message it began from, and Continue or Retry for its state; it works at 1280x800 and 390x844 (`$H ui coordination`).
- `window-team` the team is a popover from the header Team button or the avatars, not a column: the Space keeps its width when it opens, Escape, an outside click and its X close it, and the header avatars ring the role that is working (no floating badge) (`$H ui team`, needs `full`).
- `window-denials` a teammate's tool call that claude refused for lack of permission shows a card `<Role> was denied <tool>` with Add to role; Add stores the pattern in the role's `tools` (`GET /teams/{name}`) and the card says Added; the next wake of that role starts with it in `--allowedTools` and runs the tool; a read-only role refused `Write` shows `Needs write access`, a codex role `Codex ignores allowed tools`, neither has Add; the lead's Add also stops its agent so the next wake restarts it (`$H ui denials`).
- `window-subagent` a claude `Agent` call shows as a subagent row labelled from its input (`subagent_type` and `description`) with the subagent's own tool calls grouped under it: open while the call runs, collapsed once it is done (`sub-agent · N tools`); the Inspector shows the same group, collapsed, from `GET /spaces/{id}/inspector` (the `Agent` call's `children`), expandable to the nested calls; any other tool call and a codex turn show as before (`$H ui subagent`).
- `window-naming` a Space started with its name left empty shows a placeholder (`claude 02:32 PM`) with `name_auto` 1; after its first message the provider's one-shot name (`fix login redirect loop`) replaces it in `space.name`, the sidebar and the Space header, `name_auto` is 0, and the naming call leaves no turn or message; a failed proposal keeps the placeholder and the Space keeps working; a typed name and a rename sent right after the first message are never replaced (`$H ui naming`). The scenario `name-fail` has no recording on purpose: the fake claude answers it with an error; do not record it.
- `window-hovercard` hovering a Space row in the sidebar, or focusing it with the keyboard, shows a card after a short delay: the Space's name and state (idle, working, waiting for you, a failed turn, paused, wrapped), the feature's branch `feature/<slug>` and its changes (files, `+added −removed`, from `GET /work-items/{id}/diff`), and every role of the team with its creature, `working` for each role in `GET /turns?status=running`. The card closes when the pointer leaves, on Escape, on a click and on navigation; moving onto it keeps it open; it is readable in light and dark; below 768 px it never shows.
- `window-mention` hovering an `@role` mention in a Space message, or focusing it with the keyboard, shows a card after a short delay when the role is in the Space's team: its creature, name, backend and model, the first line of its persona, `Working` when the role is in `GET /turns?status=running` for the Space and `Idle` otherwise, `Can write` or `Read-only`, its tool count (claude roles) and the gates in force that name it (the team's gates over the defaults, `on` only), and an Edit link to `/teams?team=<team>&role=<role>`, which opens that team with the role's panel open. An `@word` that is not a role of the team is plain text with no card and no tab stop. The card closes when the pointer leaves, on Escape, on a click and on navigation; near the right edge it opens on the mention's left and stays inside the window; it is readable in light and dark; below 768 px it never shows.
- `window-phone` below 768 px the sidebar is replaced by a bottom tab bar (Today, Board, Spaces, Needs you, Teams, Teammates); each tab is one column with no horizontal scroll and 44 px tap targets, and widening past 768 px brings the sidebar back on the same page. At 390 px a Space hides the tab bar and has a Back link to `/spaces`; a thread opens as its own screen, the team and the inspector as bottom sheets, and the review page shows file chips and one full-width Send button.
- `window-board` `/board` shows the top-level work items in the columns Backlog, Queued, In progress, Needs you, Review, Done and Dropped, filtered by type, Team and project (the filters are in the URL). Dragging a card between Backlog and Queued moves it (`PATCH /work-items/{id}`); dropping a queued card on another card of the same Team changes its queue position (`PUT /work-items/{id}/queue-position`); a drop into any other column is refused with a message and nothing changes.
- `window-work-item-review` a top-level item in review shows a Review panel with the lead's wrap-up proposal next to the proof. Send back needs a note; with one, the item goes back to work and the lead's next prompt is `Sent back from review by the user:` and the note, and the proposal it waited on is rejected. One click on Done saves the proposal's memory items, approves it, closes the Space and sets `done`. A sub-item in review has no Review panel and no Done, and `PATCH {"status":"done"}` on it is 400.

Acceptance lines of the slice: "start a Space, chat, see streamed tool calls and text live" is
`window-live`; "a new Space of the same feature starts from the brief" is `window-brief`;
"attach a free Space to a work item" is `window-attach`; "hitting a cap pauses the Space and shows why" is
`window-cap`. Not driven here: codex Spaces in the window and reload mid-turn (drive them by hand
in the browser).

## How to get to it (user POV)

- `cd web && npm ci && npm run build`, `go build -o reef ./cmd/reef`, `./reef serve`, open `http://127.0.0.1:7700`.
- Add a project, add a feature, click New Space (or New quick session), type, Enter.

## Driving it with verify-reef

Preconditions:

- Baseline from the README, plus `node` and a Chrome: `/Applications/Google Chrome.app` on macOS; on Linux Playwright's Chromium with `REEF_VERIFY_CHROME` set (see `SKILL.md`, Window). Check it like `doctor` would: `"$REEF_VERIFY_CHROME" --version` prints a version. `error while loading shared libraries` means the system libraries are missing: `npx playwright@1.64.0 install-deps chromium`.
- The web app is built before `$H build`: `(cd web && npm ci && npm run build)`. The binary embeds `web/dist`; without it every page is 503 `UI not built`.
- The server starts with the model set, because it starts the `claude` agents: `ANTHROPIC_MODEL=sonnet REEF_VERIFY_RUN=<id> $H serve-start --data-name ui`.
- `ui teams` also needs the teams `duo` and `full` applied to the `ui` folder: `$H reef --data-name ui -- team apply ...` before `serve-start` (files and commands in `teams.md`, Window).
- `ui inbox` needs `duo` too, and reads the badge as `1`, so it fails on a server that already lists other items: run it first, or on its own folder (`$H reef --data-name inbox -- team apply $E/duo.json`, then `serve-start --data-name inbox`).
- `ui first-run` needs a server with no profile and no project: run it on its own folder (`serve-start --data-name first-run`).
- `ui inspector` needs the team `full` applied to the `ui` folder: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui review` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui theme` needs the team `duo` applied (like `ui inbox`) and leaves a waiting item for the inbox screen.
- `ui workshop` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui pr` needs a fake gh: serve-start with `REEF_FAKE_GH=<folder>`, `REEF_GH_INTERVAL=1s` and `scripts/ui/fake-gh` first on `PATH`, then `ui pr` with the same `REEF_FAKE_GH`; the fake keeps the PR in `<folder>/pr.json` and logs merges to `<folder>/merges.log`.
- `ui coordination` needs `duo` applied to the `ui` folder (the lead's direct request runs the architect at once).
- `ui subagent` commits a `sub.txt` to the run's folder (the Space runs in a worktree), asks the lead to read it through a subagent, and replays `fake/recordings/subagent-read.jsonl`, a real claude recording with `parent_tool_use_id` on the subagent's calls; it needs no team.
- `ui denials` applies its own team `denials` (a lead and a read-only reviewer, both allowed only `Read`) through `PUT /teams/denials`, and reads the fake claude's args from `fake-claude.log`, so it only runs on the fake `claude`.
- `ui hovercard` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui mention` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui phone` needs `duo` applied to the `ui` folder, and reads the Needs you badge as `1`, so run it first or on its own folder, like `ui inbox`.

## Gotchas

- Not run by `go test` or `npm test`. Runs on the fake `claude` by default (`SKILL.md`, Fake
  claude); real claude only with `REEF_VERIFY_CLAUDE=real` or `record`, and then every scenario
  takes minutes. Run each once.
- Scenarios assume the model answers short, tool-free prompts as asked. A `FAIL` on wording (`brief`) needs the screenshot before it is called a bug.
- `cap` writes to `reef.db` while the server runs; it is the one write the API cannot do (`tokenBudget` is set by the server only).
- Quote the PASS lines and say which screenshots you opened. A screenshot you did not open is not proof.
