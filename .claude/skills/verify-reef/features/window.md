# Window

A user opens the Reef window in a browser at the address `reef serve` prints. They start a
channel on a feature, chat and watch the agent's tool calls and text arrive live. A new
channel of the same feature starts from the brief. A quick session can be promoted to a
feature, and a channel that hits a cap pauses and says why. A channel on a team names the running teammate, opens replies in a Thread pane and asks Approve or Reject for a gated wake. Contract: `docs/server.md`
(Web UI, Channels live, Wrap-up and promotion, Caps).

## Sub-features

- `window-live` a claude channel on a feature: a tool-using prompt shows tool rows while the turn runs; when it ends the reply is one stored `lead` message and the live view is gone.
- `window-brief` a new channel on a feature whose brief exists answers the goal from that brief.
- `window-promote` a quick session promoted with a slug and name ends the turn with a proposal panel; the sidebar moves the channel under the new feature; the quick-session turns' checkpoints, taken in the project folder, no longer show a Roll back button; Approve makes brief version 1.
- `window-cap` a channel whose token budget is used shows a banner with the reason and a disabled composer, keeps it after a reload, and the next message runs after Continue.
- `window-pages` a bad project path shows the server's error; a feature's stage survives a reload; a task added on the tasks page is marked done and shows under the done filter.
- `window-stop` Stop mid-turn shows `Failed: interrupted` and the partial reply once; the next message resumes the session.
- `window-wrap` Wrap up shows the proposal panel, Reject leaves the brief unchanged; `/wrap` then Approve makes brief version 1 and closes the channel: Wrapped and Reopen replace Wrap up and the composer, the channel is under Wrapped (1) in the sidebar. Reopen brings the composer back; Close feature on the feature page lists it under Closed (1).
- `window-teams` the team picker makes a `duo` channel; the live turn names the lead, then the architect; a reply in the Thread pane is answered by the architect and the root shows `2 replies in thread`; in a `gated` channel Approve runs the architect and the row goes (the recipe is in `teams.md`).
- `window-retry` a failed turn shows a card with Retry; Retry runs the same wake as a new turn that ends `done`, and the row goes.
- `window-rollback` a channel with checkpointed turns lists them under Checkpoints, newest first, each with Roll back; Roll back asks to confirm, then the feature's worktree has the same HEAD, `git status`, `git log` and files as before the turn, `reef` posts `Rolled back to before turn N.`, and the next turn's prompt starts with that note.
- `window-inbox` the Needs you row and `/inbox` list what waits on the user, live from `/inbox/events`: a new approval in a channel that is not open shows with Approve and Reject and fires one desktop notification; Approve from the list runs the wake and the item goes; clicking an item, or its notification, opens its channel scrolled to and marking the item (the approval row, the failed turn row, the pause banner or the newest message); an item of the channel open and visible fires no notification.
- `window-diff` a feature's review page (`/features/{id}/review`, reached from the diff side panel's expand button or the feature page's header meta line) lists `GET /features/{id}/diff`: a turn that writes a file in the worktree, uncommitted, shows there as `A new.txt` with its added line.
- `window-memory` the project page (`/projects/{id}`, from the project switcher's Open project) shows a project memory editor, empty for a new project; saving it stores the body (`GET /projects/{id}/memory`), and it survives a reload. The page also has a Base branch field: a name that is not a branch name is refused, `dev` is stored in `project.base_branch` and survives a reload.
- `window-inspector` a channel's Inspector panel shows `GET /channels/{id}/inspector`: totals (cost, tokens, turns) summed from the roles, one row per role that ran with its turn count, tokens and cost (`n/a` when the API has none) from the API, and every turn newest first; a developer turn expands to its prompt and a tool call with its name, input and result.
- `window-review` the review page lists files with A, M or D (a deleted file struck through, a file without hunks shows No text changes); clicking a line opens a comment box; drafts show under their line and are counted per file; Send to Developer posts them as one message, `path:line` per comment, to the developer's latest thread and clears the drafts.
- `window-board` `/tasks?view=board` shows the Todo, Doing and Done columns from a task's `status`; the project and feature filters apply to it too; dragging a card to another column, or picking a column from its move select, sends `PUT /tasks/{id}` and the new column survives a reload.
- `window-task-edit` the tasks list, board and task page have no Edit button; clicking a task's title opens it in place: Enter saves through `PUT /tasks/{id}` and the title survives a reload, Escape discards; the task page edits its details in place too, and blur saves them.
- `window-workshop` the `/teams` page edits a role's persona and picks its creature (`face`) and saves both to the role row, its `mcpServers` unchanged; an invalid team (two leads, unrestricted `Bash` on a role without `write`) shows the same error as `reef team apply`; picking skills (a name not on disk shows as missing; a Codex role is offered only Codex skills) and allowed tools (checkboxes, a custom pattern field, hidden on a Codex role) and removing an MCP server saves to the role row; Settings lists the project's skills by provider; Duplicate makes a new team; the next developer wake's prompt carries the new persona.
- `window-capture` the `/capture` window picks a project and takes a kind and text; a successful capture shows "Captured", clears the text box and stores a task; a failing request (a deleted project) shows its error.
- `window-first-run` the project step shows Choose… only with the desktop bridge, and choosing a folder fills the repo path.
- `window-pr` the channel header's `PR #N` chip opens a PR panel in the channel's side panel from `GET /features/{id}/pr` (title, number, state, base and head, review, each check with a passed, failed or pending icon, an external Open on GitHub link); Merge is disabled until gh calls the PR mergeable, Cancel in its confirm dialog merges nothing, confirming runs `gh pr merge 12 --merge` once and the panel shows Merged.
- `window-theme` Settings shows Appearance (Dark, Light, Match macOS) and Notifications; picking Light restyles the open page at once and survives a reload; Match macOS follows `prefers-color-scheme` (emulated over CDP) both ways; text on the channel, inbox and feature page is at least 4.5:1 against its background in dark and light.
- `window-coordination` teammates' direct messages show in the channel as one compact item (`Lead and architect are coordinating · N messages`) and never as bubbles; the item updates in place and says working, waiting approval, paused, failed, stopped, rejected or completed; it opens a Coordination panel that shows the running recipient's text growing live, then the full ordered exchange (sender, recipient, time, delivery status), a link to the public message it began from, and Approve or Reject, Continue or Retry for its state; it works at 1280x800 and 390x844 (`$H ui coordination`).
- `window-denials` a teammate's tool call that claude refused for lack of permission shows a card `<Role> was denied <tool>` with Add to role; Add stores the pattern in the role's `tools` (`GET /teams/{name}`) and the card says Added; the next wake of that role starts with it in `--allowedTools` and runs the tool; a read-only role refused `Write` shows `Needs write access`, a codex role `Codex ignores allowed tools`, neither has Add; the lead's Add also stops its agent so the next wake restarts it (`$H ui denials`).
- `window-subagent` a claude `Agent` call shows as a subagent row labelled from its input (`subagent_type` and `description`) with the subagent's own tool calls grouped under it: open while the call runs, collapsed once it is done (`sub-agent · N tools`); the Inspector shows the same group, collapsed, from `GET /channels/{id}/inspector` (the `Agent` call's `children`), expandable to the nested calls; any other tool call and a codex turn show as before (`$H ui subagent`).
- `window-naming` a channel started with its name left empty shows a placeholder (`claude 02:32 PM`) with `name_auto` 1; after its first message the provider's one-shot name (`fix login redirect loop`) replaces it in `channel.name`, the sidebar and the channel header, `name_auto` is 0, and the naming call leaves no turn or message; a failed proposal keeps the placeholder and the channel keeps working; a typed name and a rename sent right after the first message are never replaced (`$H ui naming`). The scenario `name-fail` has no recording on purpose: the fake claude answers it with an error; do not record it.
- `window-hovercard` hovering a channel row in the sidebar, or focusing it with the keyboard, shows a card after a short delay: the channel's name and state (idle, working, waiting for you or your approval, a failed turn, paused, wrapped), the feature's branch `feature/<slug>` and its changes (files, `+added −removed`, from `GET /features/{id}/diff`), and every role of the team with its creature, `working` for each role in `GET /turns?status=running`. The card closes when the pointer leaves, on Escape, on a click and on navigation; moving onto it keeps it open; it is readable in light and dark; below 768 px it never shows.
- `window-phone` below 768 px the sidebar is replaced by a bottom tab bar (Today, Channels, Needs you, Tasks, Teams); each tab is one column with no horizontal scroll and 44 px tap targets, and widening past 768 px brings the sidebar back on the same page. At 390 px a channel hides the tab bar and has a Back link to `/channels`; Approve from its card runs the wake; a thread opens as its own screen, the team and the inspector as bottom sheets, and the review page shows file chips and one full-width Send button.

Acceptance lines of the slice: "start a channel, chat, see streamed tool calls and text live" is
`window-live`; "a new channel of the same feature starts from the brief" is `window-brief`;
"promote a quick session" is `window-promote`; "hitting a cap pauses the channel and shows why" is
`window-cap`. Not driven here: codex channels in the window and reload mid-turn (drive them by hand
in the browser).

## How to get to it (user POV)

- `cd web && npm ci && npm run build`, `go build -o reef ./cmd/reef`, `./reef serve`, open `http://127.0.0.1:7700`.
- Add a project, add a feature, click New channel (or New quick session), type, Enter.

## Driving it with verify-reef

Preconditions:

- Baseline from the README, plus `node` and a Chrome: `/Applications/Google Chrome.app` on macOS; on Linux Playwright's Chromium with `REEF_VERIFY_CHROME` set (see `SKILL.md`, Window). Check it like `doctor` would: `"$REEF_VERIFY_CHROME" --version` prints a version. `error while loading shared libraries` means the system libraries are missing: `npx playwright@1.64.0 install-deps chromium`.
- The web app is built before `$H build`: `(cd web && npm ci && npm run build)`. The binary embeds `web/dist`; without it every page is 503 `UI not built`.
- The server starts with the model set, because it starts the `claude` agents: `ANTHROPIC_MODEL=sonnet REEF_VERIFY_RUN=<id> $H serve-start --data-name ui`.
- `ui teams` also needs the teams `duo`, `gated` and `full` applied to the `ui` folder: `$H reef --data-name ui -- team apply ...` before `serve-start` (files and commands in `teams.md`, Window).
- `ui inbox` needs `gated` too, and reads the badge as `1`, so it fails on a server that already lists other items: run it first, or on its own folder (`$H reef --data-name inbox -- team apply $E/gated.json`, then `serve-start --data-name inbox`).
- `ui first-run` needs a server with no profile and no project: run it on its own folder (`serve-start --data-name first-run`).
- `ui inspector` needs the team `full` applied to the `ui` folder: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui review` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui theme` needs the team `gated` applied (like `ui inbox`) and leaves an approval waiting for the inbox screen.
- `ui workshop` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui pr` needs a fake gh: serve-start with `REEF_FAKE_GH=<folder>`, `REEF_GH_INTERVAL=1s` and `scripts/ui/fake-gh` first on `PATH`, then `ui pr` with the same `REEF_FAKE_GH`; the fake keeps the PR in `<folder>/pr.json` and logs merges to `<folder>/merges.log`.
- `ui coordination` needs `gated` applied to the `ui` folder (the lead's direct request waits for approval).
- `ui subagent` commits a `sub.txt` to the run's folder (the channel runs in a worktree), asks the lead to read it through a subagent, and replays `fake/recordings/subagent-read.jsonl`, a real claude recording with `parent_tool_use_id` on the subagent's calls; it needs no team.
- `ui denials` applies its own team `denials` (a lead and a read-only reviewer, both allowed only `Read`) through `PUT /teams/denials`, and reads the fake claude's args from `fake-claude.log`, so it only runs on the fake `claude`.
- `ui hovercard` needs the team `full` applied: `$H reef --data-name ui -- team apply "$PWD/teams/full.json"` before `serve-start`.
- `ui phone` needs `gated` applied to the `ui` folder, and reads the Needs you badge as `1`, so run it first or on its own folder, like `ui inbox`.

## Gotchas

- Not run by `go test` or `npm test`. Runs on the fake `claude` by default (`SKILL.md`, Fake
  claude); real claude only with `REEF_VERIFY_CLAUDE=real` or `record`, and then every scenario
  takes minutes. Run each once.
- Scenarios assume the model answers short, tool-free prompts as asked. A `FAIL` on wording (`brief`) needs the screenshot before it is called a bug.
- `cap` writes to `reef.db` while the server runs; it is the one write the API cannot do (`tokenBudget` is set by the server only).
- Quote the PASS lines and say which screenshots you opened. A screenshot you did not open is not proof.
